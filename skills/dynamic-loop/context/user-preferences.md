# 用户偏好

## 开发流程

- 良好的开发流程：调研，确定改动plan，按plan开发，跑改动文件测试，跑改动文件lint，按项目要求创建PR
- 开发时要使用 Worktree 来做
- 写代码/测试时先读现有文件的写法（factory、helper、命名习惯），照搬其风格，不自造新约定
- 关键节点设置人工确认点（如计划确认、diff 确认），确认点不能跳过、不能合并，未收到明确同意不得进入下一步
- 只写重要的注释，注释简单明了

## Commit 与 PR

- Commit 格式用 conventional commits + Co-Authored-By trailer
- 每个修复单独提交一笔独立 commit，不回滚、不 squash、不 force push
- 项目规范（分支名/commit 格式/PR 模板）运行时从 repo 现场读取，不写死、不硬编码
- PR body 严格逐字复制 repo 自身的 PR template，不新增/删除/重排章节，再在骨架内填充；每节须有实质内容或显式 N/A
- 先执行可撤销操作（准备 worktree、本地规范化），后执行不可撤销操作（push、开 PR、改 Jira、ready）

## Git 与 Worktree

- 读代码前先把 repo 刷到主分支最新且现场干净
- working tree 不为空时不自行 stash/reset/clean，原样返回让用户处理
- 只用 git pull --ff-only，禁止非 fast-forward 合并

## 测试

- 测试代码优先写入已有测试文件，新建是最后选项；复用已有 factory/helper/mock 基础设施
- 一个测试用例只断言一个维度，按维度分组
- 写/确认一个 failing reproduction（测试或复现用例）再修 bug，才知道何时真正修好
- 测试质量标准：Fast, Independent, Repeatable, Self-validating, Timely（F.I.R.S.T.）

## 调研

- 每条结论须指出来源（URL/文件路径/Jira key/PR 号/log 片段/行号），不许猜
- 穷举调用链：每个关键 symbol ≥2 条搜索命令，跨 repo 嫌疑时 ≥2 个 repo，每条"已穷举"声明配 ≥1 条反证
- 深度跟进：每遇 URL/ticket key/incident ID/错误码/文件路径/PR 号都打开读
- 同一事实多源出现取最低 confidence Tier（保守原则）
- 对关键排查目标，至少用两种不同方法/关键词变体去搜索确认覆盖，不能一条命令就收工
- 遇到不熟悉的人名/服务/库/flag，要主动去查背景，而不是绕过
- 对不确定的事不瞎猜，如果无法获取答案则向用户询问，留痕避免重复纠结
- 建立一份"常见偷懒借口"清单（如"应该已经全了""时间不够简版交差"），这类念头出现就停下来回到原则重新检查
- 应用自动判定规则前，先查询权威数据源核实真实状态，不能仅凭已提取的原始字段就下结论

## 计划

- 计划中每一步就是一个动作（2-5 分钟颗粒度），不应过于复杂
- 重复同一 pattern 的机械变更合并为一个 task；setup/配置/脚手架/文档步骤并入需要它们的 task
- 汇总/整合 subagent 输出时应重新综合提炼，不得原样粘贴，也不应重新判定或改写下级已给出的结论
- 补充说明/批注类内容不能是对已有正文的重复总结，只应写正文没覆盖到的补充信息
- 避免常见 AI 写作痕迹：高频空词（此外/至关重要/深入探讨等）、宣传式夸大语言、模糊归因、公式化"挑战与展望"段、否定式排比、系动词回避、不对等尺度的"从X到Y"、破折号/粗体/表情过度使用、内联标题换皮重复、协作口语痕迹、知识截止免责声明、谄媚语气、填充短语、过度限定、空洞积极结论

## 沟通

- 意图/模式判断不了时，只问用户一个精准问题澄清，而不是罗列多个问题
- 苏格拉底式提问：只在真有疑点时才问，一次只问一个问题，等回复再问下一个，无疑点直接跳过确认

## 文档

- 文档解释"why"（意图、理由），不复述"what"代码/步骤已经展示的
- 文档、commit message 以写 prose 的用心程度对待，清晰和精确与内容同等重要
- 文档作为工作的一部分构建，不事后补
